# Rails 7.1 → 7.2 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the app from Rails 7.1.5.2 to 7.2.3.1 with `config.load_defaults 7.2`, clearing the 9 remaining Rails-component Dependabot alerts while keeping 100% of tests passing.

**Architecture:** Two-phase change. Phase 1 bumps the Rails gem (and the one blocking dependency, acts-as-taggable-on) and gets the suite green while still on `load_defaults 7.1` — this alone fixes the CVEs. Phase 2 adopts `load_defaults 7.2` and reconciles framework defaults. Keeping them in separate commits makes any regression bisectable.

**Tech Stack:** Ruby 3.2.6, Rails 7.2, MySQL, Sidekiq, RSpec, Cucumber (Capybara), Vitest. Engines: Thredded, Bloggity, RailsAdmin, CKEditor.

## Global Constraints

- Target: `gem 'rails', '~> 7.2.0', '>= 7.2.3.1'` — the `>= 7.2.3.1` floor is required: a bare `~> 7.2.0` lets bundler settle on 7.2.3 (the shorter version), which does NOT carry the security fixes.
- `gem 'acts-as-taggable-on', '~> 11.0'` — 10.0 caps `activerecord < 7.2`; 11.0 = `>= 7.0, < 8.0`.
- Ruby stays 3.2.6 (satisfies Rails 7.2 `>= 3.1`). Do not change Ruby.
- Do NOT touch the non-Rails alerts (addressable, devise, bcrypt, sidekiq-cron, rexml) — out of scope.
- **Run RSpec and Cucumber SERIALLY, never concurrently** — they share the MySQL `memverse_test` DB; concurrent runs cause non-deterministic failures. Vitest may run alongside either.
- Definition of done: RSpec 1227 examples / 0 failures / 25 pending; Vitest 409 passed; Cucumber 72 scenarios / 559 steps passed; all 9 Rails Dependabot alerts auto-closed after push (open drops 15 → 6).
- Commit message trailer on every commit: `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`.

**Interfaces:**
- Produces: a Gemfile.lock resolving `rails (7.2.3.1)` and `acts-as-taggable-on (11.x)`, on which Task 2 builds.

- [ ] **Step 1: Edit the rails pin**

In `Gemfile`, change:
```ruby
gem 'rails', '~> 7.1.0'                                                        # Upgraded to Rails 7.1 for modernization
```

to:

- [ ] **Step 3: Resolve the bundle**

Run: `bundle update rails acts-as-taggable-on`
Expected: completes "Bundle updated!". Verify **every** Rails framework gem moved to `7.2.3.1` (not just a sample — a partial bump would silently leave a vulnerable component):
`grep -E "^    (rails|railties|actionpack|actionview|activerecord|activemodel|activejob|activestorage|actioncable|actionmailer|actiontext|actionmailbox|activesupport) \(" Gemfile.lock` — all must read `7.2.3.1`; `grep -E "^    acts-as-taggable-on \(" Gemfile.lock` shows `11.`.

If bundler reports a conflict, read which gem blocks it and STOP — report the conflicting constraint rather than force-bumping unrelated gems. Note: `actiontext` and `actionmailbox` are separately pinned `~> 7.1.0` in the Gemfile and must be bumped to `~> 7.2.0` too (they are Rails components). A bare `~> 7.2.0` rails pin resolves to 7.2.3; the `>= 7.2.3.1` floor is required (see Global Constraints).

## Task 2: Adopt config.load_defaults 7.2

**Files:**
- Create: `config/initializers/new_framework_defaults_7_2.rb` (via `bin/rails app:update`)
- Modify: `config/application.rb:12` (`config.load_defaults 7.1` → `7.2`)
- Possibly modify: other `config/` and `bin/` files surfaced by `app:update` (review each)
- Test (oracle): full existing suite

**Interfaces:**
- Consumes: Task 1's Gemfile.lock at rails 7.2.3.1.
- Produces: app running on 7.2 framework defaults.

- [ ] **Step 1: Run the framework update generator**

Run: `bin/rails app:update`
For each prompted file conflict, choose **`d`** (diff) first, then decide:
- Accept generator changes ONLY for `new_framework_defaults_7_2.rb` (new file — accept).
- For existing project files (`config/application.rb`, `config/environments/*`, `bin/*`, `config/boot.rb`), choose **`n` (do not overwrite)** to preserve customizations, then hand-apply any genuinely needed 7.2 change after reviewing the diff.

Expected: `config/initializers/new_framework_defaults_7_2.rb` created.

- [ ] **Step 2: Review the generated 7.2 defaults file**

Run: `cat config/initializers/new_framework_defaults_7_2.rb`
Read every commented option. Known 7.2 defaults to note:
- `config.active_record.validate_migration_timestamps = true` — **verify no migration in `db/migrate/` has a future/invalid timestamp** (`ls db/migrate | tail`); if any exist they must be renamed or this will raise on boot.
- `config.active_storage.web_image_content_types` (adds webp) — fine.
- YJIT on by default — fine on Ruby 3.2 (already a perf goal per CLAUDE.md).
- Postgres-specific defaults — N/A (MySQL).

Leave the file as-is for now (options stay commented = inherit 7.2 base where `load_defaults 7.2` sets them); the file is the staged place to override later if a default proves risky.

- [ ] **Step 3: Flip load_defaults to 7.2**

In `config/application.rb`, change line 12:
```ruby
    config.load_defaults 7.1
```
to:
```ruby
    config.load_defaults 7.2
```
Also update the comment on line ~28 (`# Cache format version is handled by load_defaults 7.1`) to reference 7.2.

- [ ] **Step 4: Boot smoke test**

Run: `bundle exec rails runner 'puts "Rails #{Rails.version}"; puts "booted OK"' 2>&1 | tail`
Expected: prints `Rails 7.2.3.1` then `booted OK`. The point is that `rails runner` fully boots the app (running all initializers) before evaluating the script — if `validate_migration_timestamps` or any initializer fails, the command exits non-zero and never prints `booted OK`. Do NOT wrap the assertion in a `rescue` (it would mask a boot failure) and do NOT call non-core/private APIs like `load_defaults_called`.

- [ ] **Step 5: Run RSpec (serial)**

Run: `bundle exec rspec 2>&1 | tail -20`
Expected: `1227 examples, 0 failures, 25 pending`.
Triage any new failures introduced by the default changes (behavioral, not API). If a specific 7.2 default breaks behavior and the fix is non-trivial, set that one option back to its 7.1 value in `new_framework_defaults_7_2.rb` (uncomment + set old value) and record it — adopt later. One option at a time.

- [ ] **Step 6: Run Vitest**

Run: `npm run test:run 2>&1 | tail -8`
Expected: `409 passed`.

- [ ] **Step 7: Run Cucumber (serial)**

Run: `bundle exec cucumber features 2>&1 | tail -12`
Expected: `72 scenarios (72 passed)`.
